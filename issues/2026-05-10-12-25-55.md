# Feature: Record Inputted Form Data to Database After Email Dispatch

**Date:** 2026-05-10  
**Status:** Planned

---

## Overview

`FormConfig` already exposes a `saveToDatabase` flag (default `false`) with a `@todo` marker, and the `wp_tofu_records` table is created on plugin activation by an existing migration. However, neither the `Record` model nor the form processing pipeline actually saves any field data.

This issue tracks all the work required to make `saveToDatabase: true` fully functional: store validated, submitted form values as a JSON blob in `wp_tofu_records` immediately after emails are sent successfully.

---

## Background

### Existing infrastructure

| Component | Location | Current state |
|---|---|---|
| `$saveToDatabase` flag | `src/Structure/FormConfig.php` | Declared, never read at runtime |
| `Record` model | `src/Models/Record.php` | Exists; only defines `form_id` column |
| `wp_tofu_records` table | `migrations/2024-08-29_00-00-00_init-records.php` | Created with `id` + `form_id` only |
| Save trigger point | `src/Models/Form.php → processConfirm()` | Emails sent here; no record write |
| `DatabaseModels::insert()` | `src/Base/DatabaseModels.php` | Generic insert already implemented |

### Flow where the record should be written

```
processConfirm()
  └─ [all emails sent successfully]
  └─ [delete temp uploaded files]
  └─ ← insert record here (when saveToDatabase === true)
  └─ storeSession(flushValue)
  └─ return success
```

---

## Goals

1. Extend `wp_tofu_records` with the columns needed to store form data.
2. Expand the `Record` model to declare those columns and provide a dedicated save method.
3. Integrate the record-save call into `processConfirm()` after emails succeed.
4. Keep the feature strictly opt-in via `saveToDatabase: true` in `FormConfig`.

---

## Detailed Tasks

### 1. Add a DB migration for new columns

Create a new migration file (e.g. `migrations/2026-05-10_00-00-00_records-add-data-column.php`) that `ALTER TABLE`s `wp_tofu_records` to add:

| Column | Type | Notes |
|---|---|---|
| `data` | `LONGTEXT` | JSON-encoded submitted field values (excluding uploaded file binaries) |
| `submitted_at` | `DATETIME` | UTC timestamp of the successful submission; `DEFAULT CURRENT_TIMESTAMP` |

Use `$wpdb->prepare()` with `%i` for the table identifier, consistent with the existing migration style.

### 2. Extend `Record` model columns

Update `src/Models/Record.php`:

- Add `data` as `COLUMN_STRING` (the base class stores it as a PHP string; JSON encoding is handled before insert).
- Add `submitted_at` as `COLUMN_DATETIME`.
- Add a static helper method `Record::saveRecord(string $formKey, array $values): int|false` that:
  - JSON-encodes `$values` (use `json_encode` with `JSON_UNESCAPED_UNICODE`).
  - Calls `static::insert(['form_id' => $formKey, 'data' => $json, 'submitted_at' => current_time('mysql', true)])`.
  - Returns the inserted row ID on success, or `false` on failure.

### 3. Integrate into `Form::processConfirm()`

In `src/Models/Form.php`, after the loop that sends emails and before the temp-file deletion block:

```
// (pseudo-code, not literal)
if ($this->config->saveToDatabase) {
    $recordId = Record::saveRecord($this->config->key, $values);
    if ($recordId === false) {
        Logger::error('Failed to save record', ['form_key' => $this->config->key]);
        // Non-fatal: log and continue — do not abort the successful submission
    }
}
```

**Important design decision:** A record-save failure must **not** abort the submission (emails already sent). Log the error and continue to the success path.

### 4. Update `FormConfig` documentation

In `src/Structure/FormConfig.php`, update the `$saveToDatabase` docblock:
- Remove the `@todo` line.
- Describe the behaviour: when `true`, validated field values are saved to `wp_tofu_records` after emails are dispatched.

### 5. Add unit / integration tests

- Test `Record::saveRecord()` with a mock `$wpdb` to assert correct column values.
- Test `processConfirm()` with `saveToDatabase: true` — verify `Record::saveRecord()` is called after email success.
- Test `processConfirm()` with `saveToDatabase: false` — verify no DB write occurs.
- Test `processConfirm()` when `saveRecord()` returns `false` — verify the submission still succeeds (non-fatal).

---

## Out of Scope (future issues)

- Admin UI to browse/export saved records.
- Ability to configure which fields are excluded from the saved data (e.g. passwords, tokens).
- Storing uploaded file metadata or paths alongside the record.
- GDPR / retention-period tooling (auto-delete after N days).

## Acceptance Criteria

- [ ] Migration runs cleanly on a fresh install and on an existing install (idempotent via `IF NOT EXISTS` / `IF NOT EXISTS` column guards or a version check).
- [ ] `saveToDatabase: false` (default) produces zero DB writes — existing behaviour unchanged.
- [ ] `saveToDatabase: true` inserts one row into `wp_tofu_records` per successful submission with correct `form_id`, `data` (valid JSON of submitted values), and `submitted_at` (UTC).
- [ ] A record-save failure does not prevent the result page from loading or the flush value from being set.
- [ ] PHPStan passes at the existing level with no new errors.
- [ ] All existing tests continue to pass; new tests cover the scenarios listed above.
